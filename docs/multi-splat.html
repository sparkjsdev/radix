Drawing many
splat objects

How Radix projects, sorts, and draws several splat objects together, and why the API uses collections, a renderer with per-viewpoint views, orders, and object releases, on WebGPU and on the WebGL2 fallback.

Each part builds on the previous one. For reference: the design notes, and the API in rendering, views, and lifetimes.

01 · Why one sort

Overlapping objects must be sorted together

A scene can contain several splat objects: loaded files, Level-of-Detail (LoD) subsets of files (the splats of a LoD tree chosen for the current camera, drawn through an index list), and splats generated in a shader. Each object has its own transform, and some move every frame. Splats are semi-transparent and must be blended back to front. Where two objects overlap, their splats have to be sorted as one list.

If each object is sorted and drawn separately, the object drawn second covers the first everywhere, including where it is behind it. If all splats are sorted together, every splat is blended in the correct order.

Requirement: all objects drawn by a renderer are projected into one shared collection, sorted once, and drawn with one draw call. The rest of the design follows from this requirement and from one limitation of WebGL2: it can't sort on the GPU (part 5).

See also: Rendering Sorting

02 · WebGPU

What a WebGPU-only app needs

On WebGPU the sort runs on the GPU in the same frame as the projection and the draw. Each render draws the renderer's current collection, from whichever camera it is given.

const collection = new SplatCollection([
  // a loaded file
  SplatCollection.arrays(scan, { matrixWorld: scanObject.matrixWorld }),
  // splats generated in a shader
  { generator: sparkles, count: 5000, matrixWorld: emitter.matrixWorld },
]);
const splatRenderer = new SplatRenderer({ renderer, collection });
scene.add(splatRenderer);

renderer.render(scene, camera);
// projected and sorted again
renderer.render(scene, otherCamera);

// drawn on the next frame
splatRenderer.collection = new SplatCollection([/* other objects */]);
Each frame on WebGPU. A new collection is drawn on the next frame.

A WebGPU-only app does not need to handle:

  • Views. Nothing depends on the camera between renders, so one renderer draws any number of cameras. A view is needed only to draw one viewpoint differently (part 9).
  • Orders and versions. The GPU sorts the current collection every frame.
  • Sort workers. A renderer in GPU mode doesn't create one.
  • Delayed releases. An object's release runs as soon as a new collection no longer contains it.

Two classes: SplatCollection holds what to draw, and SplatRenderer draws it with the settings every viewpoint shares. The following parts explain what else is needed when the same app also runs on WebGL2: orders, and a SplatView per camera to hold them.

See also: SplatRenderer Quickstart

03 · Objects

Objects are projected into one collection

A SplatCollection holds objects. Each object has a generator (the shader code that produces splat i), the generator's data, a splat count, and a matrixWorld: the object's world transform (object to world, for example an Object3D's matrixWorld). Each render, the renderer runs one GPU pass per object and writes its output at the object's offset in one shared projected collection.

Objects in the collection (click to toggle)

Before projection, each splat is transformed into camera space (head space in XR). The projected output is stored relative to the camera: a direction, a distance, and a screen-space shape. It does not depend on the object's world transform. Objects with different world transforms can therefore share one collection, and the sort key, the distance from the camera, is comparable across all objects.

Settings that the draw reads must be the same for the whole collection: the projection method, the number of sort key bits (sortBits: 16, 24, or 32), maxStdDev, minAlpha, and falloff. These are set on the renderer (a view can set its own params for its renders; the method stays the renderer's). Settings used only during projection can differ per object: blur, depth of field, and sortGuard. The renderer's objectParams holds their defaults, a view's can override them, and object.params overrides both.

Transforms: rotations with uniform scale use a fast path. Non-uniform scale, shear, and mirroring are applied to the splat's covariance. A uniform flag selects the path, so changing a world transform never rebuilds a program.

See also: SplatCollection Transforms

04 · Program cache

Programs are cached and data is passed in

Each object's pass is a GPU program that generates the splat, transforms it, optionally applies a modifier, and projects it. Building a program can take long enough to drop frames, so Radix caches programs and reuses them. Values that change often are passed to the program as bound data or uniforms.

Click an action to see whether it builds programs. The collection has two generators: fromSplats (files) and sparkles.

Programs are cached by generator, modifier, projection method, eye count, and backend. Only changes to these build new programs. Loading another file, using a new index list, moving an object, or changing blur, depth of field, or the drawn SH degree does not.

Before each object's pass the renderer sets that object's uniforms: its transform, its params, and the generator context (the view origin and the object's transforms in its own space), which every generator receives as an argument. Three.js writes each pass's uniforms when the pass is encoded, so one program draws any number of objects, each with its own values: this is how spherical harmonics are seen from the right place for every object and every camera.

Objects are not combined into one pass because each object binds its own textures, and a shader stage can bind at most 16. Combining many objects into one pass would require storing their data together in shared arrays (a splat atlas, like a texture atlas), which a generator could read in the future.

Create generators once. A generator is a program; its data is bound before each pass. A single fromSplats({ remap: "indices" }) generator can draw every file of a layout through any index list. A new LoD subset is new data, not a new program.

See also: The program cache Generators

05 · WebGL2

On WebGL2, sort orders arrive late

WebGL2 has no compute shaders, so the sort can't run on the GPU. Radix computes the sort keys on the GPU, reads them back, and sorts them on a worker thread. This takes several frames.

sort keys computed on the GPUreadbacksort on a workerdrawn with the new order

Until the new order arrives, the renderer draws with the previous order. Splats are still projected every frame, so their positions are current; only the draw order is a few frames old, which is rarely visible.

An order is only valid for one collection

An order is a list of positions in the projected collection, for example: draw position 7, then 2, then 4. Position 7 refers to a splat in one particular collection of objects.

06 · SplatCollection

Collections are immutable

SplatCollection is the collection of objects an order belongs to. A collection can't be modified after it is created, so checking whether an order belongs to a collection is an object comparison. To draw a different set of objects, create a new collection.

  • Locked on each object: generator, data, and count. These determine which splat each position refers to, so they can't change while an order uses them.
  • Live on each object: matrixWorld, params, and release. These are read every render. Moving an object doesn't require a new collection, and an older collection that is still drawn uses the current matrices.
  • The lock is applied to the object itself; nothing is copied. The same object can be used in several collections, views, and renderers. The order of objects matters: it decides each object's offset.

Versioning: the collection object is its own version. No separate counter is needed.

See also: SplatCollection

07 · SplatOrder

Which order is shown

On WebGL2 each camera gets a view (splatRenderer.viewFor(camera), made for every camera the renderer renders) that holds its order. view.sort(camera) returns an order for the collection that was current when the sort started, and view.apply(order) draws with it. autoSort does both automatically: one sort at a time per view, and a new sort whenever the camera, an object, or the collection has changed, or when the app calls requestSort().

const view = splatRenderer.viewFor(camera);
// order.collection: the collection it was made for
const order = await view.sort(camera);
// draws order.collection with this order from now on
view.apply(order);

// sort again at the next render (also with autoSort off)
view.requestSort();

#n: one collection (one color each)sort still running

  • An order is applied as soon as it finishes, even if the collection has changed again during the sort. Waiting for an order that matches the current collection would never succeed while the collection changes faster than a sort completes.
  • Newer means started later: order.version counts the view's sorts in the order they start.
  • With more than one sort in flight (manual view.sort() calls on a pool of several workers), sorts can finish out of order. An order that finishes after the order of a later sort was applied is discarded. At most one finished order waits to be applied.
  • autoSort keeps one sort in flight. Each new sort uses the latest collection and camera, so no worker time goes to orders that would be discarded.
  • requestSort() (on a view, or on the renderer for every view) asks for a new sort when something changed that autoSort can't detect, such as splats produced by a generator moving or a generator's uniform changing. With autoSort: false it is the only trigger. If a sort is in flight, the new sort starts when it finishes, because the running sort may have read its sort keys before the change.
  • An app that renders on demand passes onInvalidate: it is called when an order is applied (and on requestSort()), so the app renders the frame that shows it.

Delay: a camera's first renders draw nothing until its first order arrives. After that, the display is at most one sort behind the latest change.

08 · Object releases

When old data can be freed

On WebGL2 an old collection can still be drawn or sorted after the app has replaced it. The app can't determine on its own when an index list or a file is no longer in use. Freeing it too early causes incorrect rendering or errors.

On WebGPU, a renderer's only live collections are its current collection and its views' own collections. On WebGL2, its live collections also include each view's collection currently drawn and any collections being sorted. An object's release callback runs once no live collection of any renderer contains that object.

// Once: a generator that reads stored splats through an index list,
// and a pool of index lists
const listed = SplatGenerator.fromSplats({ remap: "indices" });
const pool = [];

// Each time the app picks a new LoD subset: `chosen` holds the indices
// of the splats to draw, written into a pooled index list if there is one
const indices = SplatGenerator.indices(renderer, chosen, pool.pop());
const subset = SplatCollection.object({
  generator: listed,
  // the file's splat arrays (kept) and this subset's index list
  data: { splats, indices },
  count: chosen.length,
  matrixWorld: model.matrixWorld,
  // once nothing draws or sorts it: back to the pool
  release: () => pool.push(indices),
});
splatRenderer.collection = new SplatCollection([subset]);
WebGPU: index lists in useWebGL2: index lists in use

  • Radix only calls the release callback. It doesn't inspect object data or free anything itself. The callback can free arrays, return them to a pool, or do nothing.
  • An object should only free data it owns, such as a LoD subset's index list. A file shared by several LoD subsets is freed by the app when it no longer needs it.
  • To share an object's lifetime between collections, views, or renderers, use the same object in each. Its release runs after the last of them stops using it.
  • Dispose renderers that are no longer needed (their views go with them). If a renderer is garbage-collected without dispose(), a warning is logged and its objects are released.

Backend difference: on WebGPU only the current collections are live, so a release runs as soon as a collection is replaced. On WebGL2 the same code releases a few frames later, and a pool needs a few more index lists.

See also: Object releases

09 · SplatRenderer and SplatView

Shared settings, and a view per viewpoint

Most of what a renderer draws is the same from every camera: the collection, the method, the params, and the modifier. These are the SplatRenderer's. A WebGL2 order is only valid for one camera position, though, and two cameras may draw different LoD subsets of the same data. That per-viewpoint part is a SplatView: splatRenderer.viewFor(camera) makes one on first use, holding the camera's order and any settings it changes.

// the renderer's settings
renderer.render(scene, leftCamera);

// the camera's view: its collection and modifier over the rest
splatRenderer.viewFor(rightCamera, { collection: rightSubset, modifier: tint });
renderer.render(scene, rightCamera);

// an explicit view: the same camera, drawn differently
splatRenderer.view = splatRenderer.viewFor("depth", { modifier: depthColor });
renderer.render(scene, leftCamera);
// back to choosing by camera
splatRenderer.view = undefined;
  • A render draws splatRenderer.view if the app set one, otherwise the view of its camera, otherwise the renderer's own settings. With the CPU sort the renderer makes a view for every camera it renders, because each camera needs its own order; with the GPU sort it makes none.
  • An app that makes camera objects anew (a clone per frame) would make a view for each one. splatRenderer.viewKey = (camera) => key maps cameras to view keys (one key for all of them, or a stable id per viewpoint), and setting splatRenderer.view draws one view for every render. The renderer warns once renders have made more than 32 views.
  • Unset settings follow the renderer, field by field. A view can't change the method or the sort mode: the method decides the projected arrays and the draw, so two methods take two renderers.
  • A view of the app's own key covers a viewpoint that is not one camera object: an XR page renders through the desktop camera, a stereo preview, and the XR camera, all one head.
  • An XR stereo pair is one viewpoint. Sort keys are distances from the head, so one order is valid for both eyes.
  • All renderers and views share compiled programs. Two SplatRenderers drawn in one render() each have their own projected collection and sorter, because three.js runs all compute work of a frame before its draws.

See also: Views View keys

10 · Modifiers

Applying an effect to all splats

A renderer's modifier (or a view's own, or null for none) is a TSL function applied to every splat it draws, similar to three.js's overrideMaterial. Examples are depth coloring, normal visualization, and wave displacement. The modifier runs in a selectable space. Changing the space only changes matrices, not the program.

  • Each new modifier builds one program per generator, once. Switching between modifiers that were already used builds nothing.
  • Splats exist in two forms: scales with a rotation, or a covariance. You can provide modifier, covModifier, or both; the program converts between forms only where necessary.

See also: Modifiers and their spaces

11 · Both backends

Running the same app on WebGPU and WebGL2

The same app code runs on both backends. The difference is how quickly changes appear. In this example, the app adds and removes splat objects over time (streaming in parts of a scene, say), so each change is a new collection, while the camera orbits.

One code path: write the app with collections and object releases as if WebGL2 support were required, and let the renderer make the views it needs. On WebGPU this adds no cost, and on WebGL2 the same code works with a delay of a few frames.

13 · Usage

Requirements for apps

  • Create generators and modifier functions once and reuse them. Creating new ones every frame builds new programs every frame.
  • Move objects by changing their matrices. Create a new SplatCollection only when the set of objects changes.
  • Set count on every object. Free data an object owns in its release callback, not when replacing the collection.
  • If the app makes camera objects anew (a clone per frame), set viewKey (or view) so they share views.
  • Call dispose() on renderers that are no longer needed, and on views of cameras or keys that are gone.
  • On WebGL2, a new camera draws nothing until its first order arrives, and collection changes appear a few frames late. autoSort handles sorting automatically, and onInvalidate tells an on-demand app when to render.
