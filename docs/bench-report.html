01 · Summary

On WebGPU, Radix is 1.35× as fast as Spark

Radix and Spark follow the reference 3DGS rasterizer by default: they draw every splat above a tiny alpha (0.5/255) and blur each by 0.3 px² with opacity compensation. So their defaults draw the same splats, and the comparison here uses them.

  • With their defaults, Radix on WebGPU is 1.35× as fast as Spark on WebGL2 (geometric mean over the scenes; Butterfly 3.69 vs 3.82 ms, Ceramic (cave) 6.28 vs 7.89 ms, Sutro 4.46 vs 6.41 ms, Grace interior 9.21 vs 16.52 ms, Radix first). Spark has no WebGPU path.
  • On WebGL2, where both sort on a worker, relative to Radix: Spark · WebGL2 1.10×.
  • Without any culling, where both draw every splat, Radix on WebGPU is 1.38× as fast as Spark; on WebGL2, relative to Radix: Spark · WebGL2 1.09×.
  • Radix's WebGL2 path stalls while it re-sorts. Its sort cycle (a keys pass on the GPU, a readback, then the order's upload) runs in the frames.

04 · Vsync

In a vsync loop

The timed numbers above measure each frame alone. An app runs in a requestAnimationFrame loop paced by the display: one frame's CPU work overlaps the previous frame's GPU work, and a frame that misses a vsync is a stutter. Every config also ran that way, in headed Chrome with vsync on (120 Hz, 3 rounds). Frame i draws pose i of the same path and nothing waits for the GPU, so a slower renderer takes longer over the path.

  • Scenes at the full 120 Hz (within 3%, under 1% of frames late), of 4, defaults: Radix · WebGPU 3, Radix · WebGL2 2, Spark · WebGL2 3.
  • Frame rate (capped by the display, which shrinks differences): Radix on WebGPU 1.11× Spark; on WebGL2, Spark 0.99× Radix.
  • Worst p99 frame intervals: Spark · WebGL2 on Grace interior 59.3 ms; Radix · WebGL2 on Grace interior 50.7 ms; Radix · WebGPU on Grace interior 17.6 ms.

07 · Thermals and repeatability

Was the laptop throttling?

Before every run the driver waited for macOS to report a nominal thermal state (ProcessInfo.thermalState): up to 90 seconds while "fair", which by itself is not throttling, and up to 5 minutes at "serious" or worse, then an idle gap. A canary (Radix on WebGPU, the butterfly, 120-frame parts) ran at the start of each round, every ten runs and at the end; when it came out more than 8% slower than its first measurement, the driver cooled down for a minute and measured it again, and measured the runs since the last good canary again. The configs ran in a different random order each round, so a slow period would spread over all of them rather than one.

08 · Method

How it was measured

Inputs

Each scan was decoded by Radix's loader and written as a standard degree-0 3DGS PLY (float32 position, log scales, rotation, logit opacity, DC color), so both renderers load the same bytes and draw degree-0 color only, without the spherical harmonics of the Grace and Sutro files. The decode quantizes slightly (SPZ sources are quantized already; the PLY sources lose some color and scale precision), identically for both renderers.

Sort keys

Each renderer sorts with its default key width. Radix uses 24 bits: the distance's float bits without the low 7, so splats more than about 0.0015% of their distance apart are ordered. Spark always sorts 32-bit keys (the float distance).

Both renderers draw at 1920×1080 at pixel ratio 1 with MSAA off, onto a black background, in headless Chrome (WebGPU on Metal; WebGL2 through ANGLE on Metal). Each config runs in a fresh tab, so nothing is shared between renderers or scenes.

Timing

  • The camera path is a function of the frame index (240 frames per part, 3 parts), so both renderers draw exactly the same poses.
  • Frames are driven by the page, one at a time: the renderer's own frame call (renderer.render), then a wait until the GPU finished all submitted work (WebGPU: queue.onSubmittedWorkDone(); WebGL2: a one-pixel readPixels), then a yield to the event loop, so asynchronous sorts on workers finish as they would in an app. A frame's time runs from its call to the GPU being done.
  • This measures each frame's whole cost (its CPU work, then all of its GPU work) without the overlap of a pipelined loop. Uncapped requestAnimationFrame timing was tried and rejected: Chrome runs WebGL frames far ahead of the GPU without vsync (one renderer timed at 16,000 fps).
  • Before measuring, each config warms up for at least 120 frames and 3 seconds of the path (pipelines compiled, caches warm, the first asynchronous sorts done). The path is then repeated until at least 6 seconds were measured (up to 6 passes).
  • Every config ran 5 rounds; each number is the median over rounds. Timer resolution is 0.1 ms.
  • The vsync run (section 04) drives the same path from requestAnimationFrame in headed Chrome with vsync on: one warm-up pass, then 2 measured passes. Thermal waits and the canary (a timed run) are as above.

Caveats

  • One machine: an Apple M3 Max laptop.
  • The CPU-sort paths draw orders a few frames old while the camera turns: the timing counts their cost, not the visual lag.
  • Radix's numbers come from its code at the time of the run; Spark is its 2.3.1 npm release.
